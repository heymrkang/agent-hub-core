## Hardened runtime guarantees

The following behaviors are enforced by the Phase 8 implementation and remain available for targeted operational regression testing when desired:

- One-shot isolated scheduler sessions prevent native conversation reuse between runs.
- Manual `지금 실행` is independent from schedule enable/disable state and next-run calculation.
- Provider Queue Grace converts excessive scheduler queue wait into `SKIPPED` rather than unbounded waiting.
- Schedule timeout is delegated to the canonical Job Runtime cancellation path.
- Overlapping executions of the same schedule use the V1 `SKIP` policy.
- Scheduler persistence and Telegram delivery redact recognized secret/token patterns.
- `schedule_runs.job_id` provides traceability from a schedule execution to its canonical Job Runtime record.

## Operational note

A Telegram `409 Conflict: terminated by other getUpdates request` may appear when more than one process/container polls the same Bot Token. This is an independent deployment/polling-instance issue and is not a Phase 8 Scheduler defect. Production operation should keep exactly one polling instance per Bot Token.
