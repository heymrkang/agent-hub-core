## Hardened findings

- [x] Scheduler execution context is one-shot per run. A new `is_system=1` execution session is created for every run and marked `DELETED` after completion/failure. Native provider sessions are never reused by the next scheduler run.
- [x] Legacy reusable `execution_session_id` references are cleared by migration `008_scheduler_execution_isolation_cleanup.sql`.
- [x] Manual `지금 실행` no longer changes `enabled` or `next_run_at`.
- [x] `/schedule` UI is List → Detail with 5 items per page and pagination.
- [x] Provider queue grace is supported for scheduler jobs through `SCHEDULER_QUEUE_GRACE_SECONDS` (default 30 seconds). Grace expiry is recorded as `SKIPPED`.
- [x] `schedule_runs.job_id` is populated from the actual Job Runtime id.
- [x] Scheduler result/error/notification text is passed through secret redaction before persistence or Telegram delivery.
- [x] Existing overlap policy remains `SKIP`; missed runs are not replayed; automatic retry remains disabled.
- [x] Schedule-specific execution timeout continues to use Job Queue cancellation.
- [x] Model Catalog remains dynamic/cache-based with stale-while-revalidate and no hardcoded provider model fallback.
